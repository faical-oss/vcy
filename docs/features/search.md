# Search

Last updated: 2026-11-25

## Purpose
Two parts. (1) The search box, in the Home hero and as a docked bar: built, it navigates to `/search?...`. (2) The results page `/search`: built on mock data (a typed request and response, one mock function, `TODO(api)`).

## The search box (hero and docked bar)
- `SearchBar` (`src/components/sections/search/search-bar.tsx`) sits in the Home hero: tabs Experiences / Packages / Hotels, four fields (type, destination, dates, travellers), a Search button and the Popular chips. Type and destination are comboboxes (focus stays in the input, `aria-activedescendant`, arrows/Enter/Esc); dates and travellers are popovers. Only one is open at a time; Esc and a click outside close it. The date picker and travellers content are lazy chunks (`next/dynamic`), so Home's first JS did not grow.
- State lives in `SearchProvider` (`(site)/layout.tsx`) so the docked bar can share it with the hero. Pure logic is in `src/helpers/search-box.ts` (reducer, `searchHref`, `readSearchFromSearch`, `filterOptions`); switching tab resets every field. Steppers, child ages and the flexibility chips are shared with the hotel booking form (`src/components/ui/guest-fields.tsx`); steppers are 44px here.
- **Dates are never empty:** a provider effect sets check-in tomorrow and check-out two nights later on mount (in the browser, so the prebuilt page never carries a stale date). Clear returns to that default, switching tab keeps the dates, and `searchHref` fills a missing or half-picked range with the default, so `checkIn` and `checkOut` are always in the URL.
- **Suggestion lists:** matching is by the start of a word ("s" finds "Sri Lanka" and "Koh Samui", not "Bali"). Typing in Destination shows 0.5 s of skeleton rows (a stand-in for the API call, `SEARCH_DELAY_MS`), then one plain list of matches without region titles; with no text the two-column regions list shows. The option already picked has the selected colour and a check (type, destination and hotel type lists).
- Suggestions come from `getSearchBoxContent()` (`src/features/search`, fixture, `TODO(api)`). Popular chips fill their field and never submit.
- **URL contract** (one helper, `SEARCH_TARGET` = `ROUTES.search`): `type` (tab: experience|package|hotel), `category` (picked type), `destination`, `q` (text typed but not picked), `checkIn`, `checkOut`, `flex`, `rooms`, `adults`, `children`, `childAges`. Defaults (1 room, 1 adult, 0 children) are omitted; the dates are never omitted. `readSearchFromSearch` accepts only the three tab values for `type`; any other `?type=` is ignored. `type` and `destination` are in `FILTER_PARAMS` (noindex, like the other filters).
- **Docked bar:** `DockedSearch` (`docked-search.tsx`, mounted in `(site)/layout.tsx`) renders, under the header, the same `SearchBar` with `variant="docked"` (one row: tabs, fields, Search button, no chips) from `xl` (1280) and, from `md` to below `xl`, the `SearchPill` (below). Both share the hero's state. A sticky wrapper (`top-header`, height 0) holds it, so showing it never moves the page; it slides out from under the header in 200 ms (no transition with reduced motion) and is `inert` while hidden.
- **Where it shows** (`showsDockedSearch(pathname)` in `src/helpers/docked-search.ts`, the one rule): a **deny-list**, and which pages have it from the top. The bar is on every page except the account area, support, privacy, terms, about us and checkout. **From the first pixel** (mode `top`): `/search` and the detail pages (`/hotels/h/*`, `/experiences/e/*`, `/packages/p/*`). **After a scroll of 320 px** (mode `scroll`): every other page. A 404 follows its pathname. A new page shows the bar until it is added to the list; the test (`docked-search.test.ts`) has a row per page under `src/app` and fails when a page is missing from it. It exists from `md` (768): below it only `/search` has the pill (`ResultsSearchPill`).
- **Offset:** while the bar shows, `data-docked-search` on `<html>` sets `--docked-search-h` (4rem at every width), for the pill and the row alike. The Lifestyle sub-nav adds it to its `top` and its anchor targets reserve `md:scroll-mt-[185px]`. On the detail pages `DetailShell` reserves it at the top (`pt-[5.5rem]`: the bar is there from the first pixel, at every width) and the sticky booking box (`lg`) and `DetailTabs` (bar and anchor `scroll-mt`) add it to their `top`. Any new sticky element under the header does the same. No measuring.
- **Results URL:** `SearchUrlPrefill` (inside `<Suspense>`) fills the bar from the URL on `/search` when `type` is valid; the URL wins over the held state. Elsewhere the bar keeps its state.
- **Hydration:** a bar inside Suspense can hydrate after the provider has changed state, so each bar renders the empty state until it has hydrated (`useSyncExternalStore`), then the live one.
- **Fields and labels:** four fields named What / Where / When / Who (`FIELD_NAMES`): short, so they never truncate; the full meaning is in the accessible name ("What (experience type)", "When (dates)", "Who (rooms and guests)", `typeLabel` and the other labels of the content). Placeholders are short ("Any experience", "Anywhere", "City or hotel"); the dates read as short as a stay can be written (`datesSummary`: "25–27 Nov 2026"), "Add dates" only when there are none. Nothing is cut: a value wraps (the two combobox fields are one-row text areas the height of their text, Enter searches) and the cell grows.
- **Layout:** hero: stacked below 768 (fields 64px), a 2x2 grid with a full-width Search button from 768, one row with the button from 1024. Tabs: three equal tabs, 56px high, a 20px icon over a 13px label below 640 (sentence case, so "Experiences" fits at 320), side by side and uppercase from 640. Docked row from 1280.
- **Pill and sheet** (`search-pill.tsx`): below `xl` the docked bar (at every width, 320 included) is `SearchPill`, the full width of the container: where, then "dates · travellers", a chevron and a round search button. It opens `SearchBar variant="sheet"` in a Radix dialog: a panel as tall as its content (at most 90dvh): below 768 a flat full-width panel directly under the navbar on phones and tablets alike (no centred modal; square corners, the navbar stays clear, the backdrop starts under it, the form is at most 42rem wide and centred; under the on-screen keyboard it follows the top of the visual viewport: `useVisibleBox`). It slides down from under the navbar and back up when it closes (none under reduced motion; Radix keeps it mounted until the exit animation ends). Dimmed backdrop, tabs and a Close button on top, the four fields stacked (64px) in a body that scrolls when a panel opens, and the Search button right under the last field (always on screen, safe-area padding). Dates, travellers and the two lists open in place under their field (an accordion); Escape closes an open one first, then the sheet; focus is kept inside and returns to the pill; a focused field is scrolled to the middle of the visible body. A search closes the sheet. The pill is not fixed in height (its text wraps).

## The results page (`/search`)
Built from the Figma prototype in `search-results-spec` (layout and behaviour; the visuals are our tokens and cards). Hotels, Experiences and Packages share one page; the tab (`type`) in the URL picks the filter groups.

**Shell and fetching.** `app/(site)/search/page.tsx` is a prerendered shell (partial prerender): the h1 "Search results", an intro line and a skeleton. In the browser `SearchHeading` swaps the heading for the tab's own ("Hotels", "Packages", "Experiences", each with its intro line); there is always exactly one h1 and the page title stays "Search results". It never reads `searchParams`, and the URL-dependent parts (`SearchResults`, `MobileSearchSummary`) render nothing until hydrated (`useHydrated`), so the markup is the same for every search (`e2e/search-page.test.ts` checks it; Next's own flight data repeats the URL, so the check ignores `<script>`). Results are fetched in the browser, never on the server.
- **Fetch rules** (`createResultsLoader`, `src/features/search/results-loader.ts`, with tests): no call without a search (`type` valid, every child has an age); the first search of the page is sent at once; the same search is not asked twice and answers are cached by parameters; quick edits make one call (the shared `FETCH_DEBOUNCE_MS` = 400 ms, also used by the booking box); a newer search aborts the older request and ignores its answer; "Try again" asks the failed search again now.
- **Dates:** missing or invalid dates do not stop the search: results are listed without prices and a banner says "Choose your dates to see prices". Prices and availability are the only things that depend on valid dates: "Not available for these dates" appears only with valid dates.
- **Data path:** browser `services/search-results.ts` -> `GET /api/search` -> `getSearchService().search()` -> `mockSearchService` (one function over the catalog, 0.5 s delay; the real `SearchService` maps the same parameters). Components never import services or mocks (ESLint); `features/search/search-results.tsx` is the client controller. The dev-only `?mock=` (available, partial, none, error) works like the availability one.

**URL contract.** The search keeps the box's parameters (`type`, `category`, `destination`, `q`, `checkIn`, `checkOut`, `flex`, `rooms`, `adults`, `children`, `childAges`). The results state adds `sort` (`price-asc`, `price-desc`, `top-rated`, `stars`), `minPrice`, `maxPrice`, `types`, `stars`, `places`, `amenities`, `board` (comma-separated slugs), `rating` (3-5), `view` (`grid`) and `page`. Defaults are left out. Everything above is in the URL; open or closed filter groups, "Hide filters", the drawer, price text while typing and the expanded phone search are not. `helpers/search-results.ts` reads and writes it (`readResultsState`, `writeResultsState`, `readSearchParams`). The Search button pushes a history entry (and starts a clean search: filters, sort and page are dropped); filters, sort, view and page replace the entry, and every change but the view goes back to page 1.

**Filters.** Each tab has the groups of the Figma prototype (`content.groups`), in its order. Hotels: Price Range (two-thumb slider and Min/Max boxes, 0-5000), Hotel Type, Destination, Amenities, Board Type, Rating (single choice: guest rating rounded to 5, 4+ or 3+). There is no Star Rating group (it duplicated Rating; `stars` is still a valid parameter of the contract). Packages: Price Range, Package Type, Duration, Destination, Inclusions, Travel Style, Rating. Experiences: Price Range, Experience Type, Duration, Destination, Group Size, Difficulty, Included, Rating. The options come from the results of the search before the sidebar filters (`facets` in the response), in the prototype's order, so an option never leads to an empty page on its own, and a group with fewer than two options is left out. The URL parameters are shared: `types`, `places`, `amenities` (also Inclusions and Included), `board` (also Travel Style), `duration`, `groupSize`, `difficulty`, `rating`, `minPrice`, `maxPrice`. No counts and no "show more" (the prototype has neither). Each group collapses and shows a count badge; applied filters appear as removable chips with "Clear all". The sidebar is not sticky and can be hidden ("Hide filters", fades); the Experiences and Packages lists use the prototype's denser rows (28px, grey boxes), the Hotels list 32px rows with dark boxes. On a phone the same panel is a left drawer (`FiltersDrawer`: focus moves in, Tab stays inside, Esc, the dimmed area and the close button shut it, focus goes back, the page does not scroll behind it, and "Show N results" closes it). Filters apply as they are ticked. Price: the slider commits when released, the boxes as typed.

**Results.** Sort (Recommended, Price low to high, Price high to low, Top Rated, Star Rating), List and Grid (from `md`; a phone always shows the list, even when the URL says `view=grid`; the default is the list at every width), a count line (`aria-live`), a pager with "Showing a-b of N results" (12 per page). List view is `ResultListCard`, laid out per kind with the sizes measured on the prototype's screenshots (297px photo, 18px padding, 10px labels, 24px serif title, 11-12px text, 163px right column, 259-268px tall): hotel (320px photo with a solid label, class stars, serif title, place, rating, amenity chips; boxed heart and price on the right), package (photo with a solid badge; outlined category and solid badge above the title, provider, place, nights, hairline, check-marked highlights around the rating), experience (outlined category and "Best seller" badge, title, provider, place, nights and group size, hairline, the dates and guests of the search, rating with "reviews", four inclusions with icons; badge, group size and inclusions come from the experience's detail page). The toolbar (Hide filters, count, Sort, List / Grid) is 34px high with 13px text; the sort select has its own chevron, 14px in from the right edge; the count reads `N results for "type" in destination`. Grid uses `HotelCard`, `ExperienceCard` and `PackageCard`. Hotels are priced per night, experiences and packages per person; ratings come from the catalog mocks (no JSON-LD). Results with no price show "Select your dates to see prices"; sold-out ones "Not available for these dates" and go last. Each card links to its detail page with the dates and travellers in the URL (`writeStayToSearch`). States: skeleton (rows or cards), count, empty (with filters: "Clear all filters"), error with retry (`role="alert"`). "Clear all filters" is always on the empty state: with filters on it clears them, without it drops the picked type, destination and typed text.

**Layout.** The filter sidebar shows from `lg` (1024); below it the filters are in the drawer (button "Filters") and the results have the whole width. Grid view: 1 column below 640, 2 to 1279, 3 from 1280 (`LISTING_GRID`, viewport based, see responsive-testing.md).

**Panels.** One placement rule for the four panels of the box, in every bar (hero, docked, the results page's) and on every page (`anchored-panel.tsx`). From lg (1024) a panel hangs under its field: left edge on the field's, shifted left until it fits inside the bar, never wider than the bar, 16px from the viewport edge (`AnchoredPanel`, measured before paint and on resize), so the page never scrolls sideways. Below lg the dates and the travellers are a bottom sheet (`SearchSheet`, Radix dialog in a portal: full width, title and a 44px Close button, scrolls inside, up to 90dvh, safe-area padding, focus kept inside and returned to the field, Escape or a tap outside closes, above the sticky header, tabs and docked bar), and the two lists (type, destination) are as wide as the bar, scroll inside (60dvh) and have a Close button (not a tab stop: Tab still leaves the field, Escape closes). A press inside the sheet (it is outside the bar in the DOM) does not count as a click outside.

**Filters drawer (below `lg`).** The filters apply as they are changed (checkbox, price slider, rating: a history replace, so no new entry per click) and the drawer stays open; the focus stays on the control that changed, and the new count is announced in a polite live region while the button shows it. Only the "Show N results" button, the close button, Escape and a tap on the dimmed area close it, and the focus returns to the Filters button (also in Safari, which does not focus a tapped button). **Cards:** a card without valid dates shows no price text at all (never "Select your dates to see prices"): `Price` and the list card render a blank line of the lockup's own height, so the card does not change height when prices arrive. The banner above the results still says to choose dates.

**Phone.** The docked pill is there at every width below `xl` (it replaced `ResultsSearchPill`, which only phones on `/search` had); on `/search` it is filled from the URL. The page reserves its 4rem (`pt-24`). Tabs (hero and sheet): the icon above the label below 400px, beside it from 400px.

## Data
- `ISearchService.search(params, { scenario })` in `src/interfaces/search.ts`: `SearchParams` (type, category, destination, q, optional `stay`, guests, filters, sort, page, pageSize) in, `SearchResponse` (items with price and availability, total, page, pageSize, facets) out. An item is the card data of its kind plus `availability`; `price` is absent without valid dates or when unavailable. The shapes are ours until the Trip Fusion docs arrive (`TODO(api)`).
- Mock: `src/mocks/services/search.mock.ts`, over the catalog: 20 hotels, 24 experiences and the 22 packages that have a detail page (at least 20 of each type), so every card links to a real detail page and the filter options come from them. Hotel prices vary by season (90-120% of the base rate); the two newest hotels (a boutique retreat in Mallorca and a beach resort in Guanacaste) were added to the catalog for this; amenity options are matched by keyword from the hotels' free-text amenities; board type is assigned from the hotel id; the search box's hotel types map to the catalog's tags (a type with no tag matches nothing). Group size, flexibility and duration rules are not applied (the detail page does).
- Real: `SearchService` (`src/services/search.service.ts`) calls `GET /search` with the same parameters through the API client (8 s timeout, no caching).

## Caching
- None for results: `GET /api/search` is `no-store`, the browser keeps answers for the page's lifetime (the loader's cache). Plan (not built): the API call cached for a short time keyed on the normalized parameters; prices and availability live.

## SEO
- `/search` is noindex (`urlPolicy` type `search`: noindex, follow; nofollow while indexing is off) with the canonical on `/search` itself: there is no clean indexable page to point at (the type and destination pages cannot be derived from a query in static metadata). Not in the sitemap. One h1 ("Search results"), a unique title and description, no breadcrumb (the prototype has none), no JSON-LD. Search and filter URLs also get `X-Robots-Tag: noindex, follow` from `FILTER_PARAMS` (`types`, `stars`, `places`, `amenities`, `board`, `rating` and `view` were added; `sort`, `minPrice`, `maxPrice` were already there). `?page=` is not a filter.

## Open questions and mocks
- The real search endpoint, parameters and response shape, how prices and availability are returned, and whether search and availability are separate calls, are unknown.
- Everything on the page is mock data (catalog items, seasonal prices, board types, availability scenarios). The catalog has no values for package type, travel style, inclusions, group size, difficulty or "included", so the mock gives each result its values in a fixed pattern (keywords first for the types). The Figma prototype's Map view was not built (it is a placeholder with invented counts and needs a map provider); the Experiences and Packages tabs of the prototype were never captured.
- API-backed suggestions in the box, and the travellers popover's shared hotel limits (8 rooms, 9 adults, 6 children) on every tab.
